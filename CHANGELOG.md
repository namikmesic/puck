# Changelog

Notable changes to Puck, newest first.
Versions follow `MAJOR.MINOR.PATCH`, and every release is tagged `v<version>` on `main`.
`RELEASE.md` describes how a release is built.

## Unreleased

- `npm run start:isolated` (`PUCK_ISOLATED=1`, optionally `PUCK_ISOLATED_DIR`) launches Puck for tests and checks with its data in a throwaway folder, Electron's mock keychain, and a window that does not take focus; `npm run test:e2e` now runs this way and never touches the real data folder or Keychain.
- The Puck server (`src/server/`), not yet used by the app: GitHub web-flow sign-in with PKCE and rotating sessions, custody of users' GitHub tokens, runner registration with one-hour tokens and signed key assertions, runner status, an environment index whose repository grants are checked against the owner's push access, installation tokens scoped per environment, an end-to-end encrypted relay with flow control, runner downloads, and an audit log; it ships as the `puck-server` image and runs locally with `docker compose up`.
- GitHub sign-in works through the registered "Puck Agents" GitHub App: a default build offers device-flow sign-in and links to <https://github.com/apps/puck-agents/installations/new>; `PUCK_GITHUB_CLIENT_ID` and `PUCK_GITHUB_APP_SLUG` still point a development build at a test app.
- Providers come in three kinds with one registry: harnesses (Claude Code, Codex), environments (Local Docker, Docker over SSH with a health check that names the SSH problem), and GitHub, signed in through the device flow, with its config repo chosen in **Settings → Providers**; host CLI login files and host environment variables no longer reach containers.
- GitHub sign-in is the device flow through the Puck GitHub App only: the personal access token option is gone from Settings, repositories come from the app's installations, and a token saved by an earlier build is discarded, so GitHub reads as signed out until you sign in again.
- Every provider now reports one status (connected, disconnected, pending or error, with a detail line), and an environment target's health check returns its detail and Docker server version under the same names Settings shows.
- Agents and environments can be defined as versioned YAML in the GitHub config repo: Puck reads the definitions at a tag, branch or commit, validates every definition file with the file, line and column of each error, resolves an environment with its agents, and ships a JSON Schema (generated by `npm run schema` into `schema/puck.schema.json`) plus an example config repo in `docs/examples/config-repo/`; today's agents and environments are unchanged.
- `puck-runner` (`src/puck-runner/`), the program you install on each machine that hosts environments, not yet used by the app: `./config.sh` checks Docker and registers the machine with the Puck server using a one-hour registration token and the runner's own Ed25519 key, `./run.sh` connects out to the server (no open ports) and reports Docker's version and capacity every 20 seconds, and `./svc.sh` installs it as a systemd service or a macOS LaunchAgent; it creates, starts, stops, rebuilds and deletes environment containers (found again by label), relays end-to-end encrypted attach channels to each environment's daemon, caches the daemon bundles the app sends, keeps each environment supplied with one-hour GitHub installation tokens from the server, updates itself, and ships as tarballs for Linux x64, Linux ARM64 and macOS ARM64 with a bundled Node runtime and sha256 sums (`npm run package:runner`); `./config.sh remove` keeps or deletes the machine's environments. Restarting the runner never interrupts a running environment.
- The environment daemon now holds the GitHub installation tokens its runner pushes (one per repository owner, no refresh token) instead of a refreshable user-token pair, and reports them as expiring ten minutes before they lapse; a turn cut off by a graceful restart (a container stop or restart, or an immediate daemon upgrade) now resumes through its harness session on the next boot, as one cut off by a crash already did.
- A new environment daemon, `puckd`, is built beside today's runner (not wired into the app yet): it runs as the container's main process, provisions the environment, drives Claude Code and Codex as an unprivileged `puck` user, keeps a sequenced event log that clients replay after reconnecting, stores transcripts in format v2, and upgrades itself in place; CI builds it and runs it in real containers.
- The environment daemon now runs the orchestration itself, still beside today's app: a prioritized backlog of work items with a strict state machine and a scheduler that respects each agent's `maxParallel` and the environment's `maxWorkers`; one git worktree and `puck/W-<n>-…` branch per item with the worker prompt and captured results (commits, diff stat, uncommitted files, summary); the orchestrator's preamble and its in-process `puck` tools (run by the root daemon while the Claude CLI runs as the unprivileged `puck` user); batched notices that wake the orchestrator, with a runaway guard; worker questions routed to the orchestrator first and escalated to you when it does not answer; publishing through the root-owned mirror (bundle, push fenced to `puck/*` with force-with-lease, pull request opened or updated) using per-owner GitHub grants the daemon receives rather than refreshes; `definition.apply` for hot and reprovision updates; and a restart that resumes an interrupted item's existing worker conversation without counting a failed attempt.
- A shutdown or daemon upgrade that lands while a work item's first worktree is being prepared no longer leaves its worker without instructions: after the restart, a worker that never received its prompt starts with the full worker prompt, and one that already had it still resumes its existing conversation.

## 0.0.1 - unreleased

The first public build of Puck: macOS on Apple silicon, macOS 12 or later.

### What the build contains

- A desktop client for coding agents, with Claude Code and Codex as providers.
- One long-lived, Slack-style conversation per agent, stored as a structured event log and replayed on launch.
- Docker environments: persistent containers with one host folder mounted at `/workspace`.
- Provider sign-in in the system browser with a loopback callback.
  Tokens are encrypted through the macOS Keychain, and Puck refuses to store them in plaintext.
- Disconnect removes Puck's own tokens and the credential copies in running environments.
- Streaming turns with markdown, tool cards, sub-agent chats, and answerable question cards.
- A diagnostic log in the app data folder, bounded to three files of 1 MiB.
- A support-bundle export in Settings → Support: the logs plus a sanitized configuration summary.
- An application icon.

### Known limitations

- Codex sub-agents show their lifecycle only (spawned, running, finished), not their transcript.
- The build is ad hoc signed and not notarized until Developer ID credentials exist (open call C-3).
  macOS asks for a one-time approval in System Settings on first launch.
- There are no automatic updates.
  Replace `Puck.app` by hand, as the README describes.
- The distribution channel is not decided (open call C-2).
  The artifact is a local ZIP with a SHA-256 checksum file beside it.
- Environments run agents as root with full tool access inside the container.
  The mounted workspace folder is writable from the container.
- Delete asks for a second click, but rebuild acts on the first click.
