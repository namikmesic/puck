# Changelog

Notable changes to Puck, newest first.
Versions follow `MAJOR.MINOR.PATCH`, and every release is tagged `v<version>` on `main`.
`RELEASE.md` describes how a release is built.

## Unreleased

- The environment window, behind `PUCK_UI=v2` (today's window stays the default): one environment on screen at a time, with the environment switcher and its status, updates and GitHub state in the top bar; the prioritized backlog on the left (drag or Alt+↑/↓ to reorder, ⌘N for a new item, **Import issue…** to search the environment's repositories); the orchestrator chat in the center with Puck's notices and links to their items; work in progress on the right (needs input, running, review, and each agent's capacity); and work detail for any item, with its actions, the worker's conversation, the changes with CI checks and review feedback (feedback agents never see is marked), and editable details. It adds a start flow that picks a definition at a tag, branch or commit and a runner by status, capacity and labels; a first-run sequence from GitHub sign-in to the first environment; Settings with Providers, Runners and Support; ⌘K to jump anywhere; and definition updates that apply in place, or rebuild when they must. When this Puck carries a newer environment daemon, **Daemon update** restarts it after running turns finish, or at once (a turn interrupted that way resumes). An environment whose connection ends unreachable, incompatible or detached now says so instead of waiting, and a failed history load no longer drops the events that arrived meanwhile.
- The app now works through the Puck server and runners instead of Docker over SSH: you sign in to Puck with GitHub in the browser (the server holds the GitHub App's secret; the app keeps only its Puck session), **Settings → Providers → Runners** lists your runners with their status (Idle, Active, Offline), Docker version and capacity, adds one with GitHub-style copy-paste commands and a one-hour registration token, renames, relabels and removes them (with a force remove for a machine that is gone), and sets up **This Mac** as a runner in one click; the app reaches remote runners through the server's end-to-end encrypted relay and This Mac over a local socket, never running `docker` itself for them, and starts environments on them from a definition, attaches to their daemon, keeps harness credentials in sync, and replays from the last event after a restart. Docker over SSH is gone, and so is the device-code GitHub sign-in.
- `npm run start:isolated` (`PUCK_ISOLATED=1`, optionally `PUCK_ISOLATED_DIR`) launches Puck for tests and checks with its data in a throwaway folder, Electron's mock keychain, and a window that does not take focus; `npm run test:e2e` now runs this way and never touches the real data folder or Keychain.
- The Puck server (`src/server/`): GitHub web-flow sign-in with PKCE and rotating sessions, custody of users' GitHub tokens, runner registration with one-hour tokens and signed key assertions, runner status, an environment index whose repository grants are checked against the owner's push access, installation tokens scoped per environment, an end-to-end encrypted relay with flow control, runner downloads, and an audit log; it ships as the `puck-server` image and runs locally with `docker compose up`.
- GitHub access works through the registered "Puck Agents" GitHub App: a default build links to <https://github.com/apps/puck-agents/installations/new>; `PUCK_GITHUB_CLIENT_ID` and `PUCK_GITHUB_APP_SLUG` still point a development build at a test app.
- Providers come in three kinds with one registry: harnesses (Claude Code, Codex), runners (where environments run), and GitHub, with its config repo chosen in **Settings → Providers**; host CLI login files and host environment variables no longer reach containers.
- GitHub goes through the Puck GitHub App only: the personal access token option is gone from Settings, repositories come from the app's installations, and a token saved by an earlier build is no longer read, so GitHub reads as signed out until you sign in again.
- Every provider now reports one status (connected, disconnected, pending or error, with a detail line).
- Agents and environments can be defined as versioned YAML in the GitHub config repo: Puck reads the definitions at a tag, branch or commit, validates every definition file with the file, line and column of each error, resolves an environment with its agents, and ships a JSON Schema (generated by `npm run schema` into `schema/puck.schema.json`) plus an example config repo in `docs/examples/config-repo/`; today's agents and environments are unchanged.
- `puck-runner` (`src/puck-runner/`), the program you install on each machine that hosts environments: `./config.sh` checks Docker and registers the machine with the Puck server using a one-hour registration token and the runner's own Ed25519 key, `./run.sh` connects out to the server (no open ports) and reports Docker's version and capacity every 20 seconds, and `./svc.sh` installs it as a systemd service or a macOS LaunchAgent; it creates, starts, stops, rebuilds and deletes environment containers (found again by label), relays end-to-end encrypted attach channels to each environment's daemon, caches the daemon bundles the app sends, keeps each environment supplied with one-hour GitHub installation tokens from the server, updates itself, and ships as tarballs for Linux x64, Linux ARM64 and macOS ARM64 with a bundled Node runtime and sha256 sums (`npm run package:runner`); `./config.sh remove` keeps or deletes the machine's environments. Restarting the runner never interrupts a running environment.
- The environment daemon now holds the GitHub installation tokens its runner pushes (one per repository owner, no refresh token) instead of a refreshable user-token pair, and reports them as expiring ten minutes before they lapse; a turn cut off by a graceful restart (a container stop or restart, or an immediate daemon upgrade) now resumes through its harness session on the next boot, as one cut off by a crash already did.
- A new environment daemon, `puckd`, is built beside today's runner: it runs as the container's main process, provisions the environment, drives Claude Code and Codex as an unprivileged `puck` user, keeps a sequenced event log that clients replay after reconnecting, stores transcripts in format v2, and upgrades itself in place; CI builds it and runs it in real containers.
- The environment daemon now runs the orchestration itself, still beside today's app: a prioritized backlog of work items with a strict state machine and a scheduler that respects each agent's `maxParallel` and the environment's `maxWorkers`; one git worktree and `puck/W-<n>-…` branch per item with the worker prompt and captured results (commits, diff stat, uncommitted files, summary); the orchestrator's preamble and its in-process `puck` tools (run by the root daemon while the Claude CLI runs as the unprivileged `puck` user); batched notices that wake the orchestrator, with a runaway guard; worker questions routed to the orchestrator first and escalated to you when it does not answer; publishing through the root-owned mirror (bundle, push fenced to `puck/*` with force-with-lease, pull request opened or updated) using per-owner GitHub grants the daemon receives rather than refreshes; `definition.apply` for hot and reprovision updates; and a restart that resumes an interrupted item's existing worker conversation without counting a failed attempt.
- A shutdown or daemon upgrade that lands while a work item's first worktree is being prepared no longer leaves its worker without instructions: after the restart, a worker that never received its prompt starts with the full worker prompt, and one that already had it still resumes its existing conversation.
- `puckd` no longer loses a turn's reply, a user or notice line, or a turn's end to a crash or a full disk: the transcript is fsynced before the turn is finalized and before the session is marked idle or interrupted, a failed turn-end transcript write keeps the handoff and the chosen end status and is retried until it lands (including after the session is closed) before that turn is finalized and its `turn.end` is published, a session with queued text or pending notices starts once that write lands, boot leaves a turn the transcript already finished idle and restores that session's turn totals from the transcript instead of resuming it, user and notice lines that stayed on disk after a failed publish are published on the next delivery (including a second identical user line), and a `turn.end` the event log refuses is retried until it is appended (and written at boot, with the transcript's stats, for any retained turn left open). A send while that end is still held is queued instead of returning a turn id that never starts.
- The environment daemon now works with GitHub, still beside today's app, by polling with conditional requests (ETags): open issues carrying an environment's intake label (`policies.github.intake: label`, default label `puck`) become work items, and `puck:<agent>` also assigns them; issues can be imported by hand (`issue.import`, or the orchestrator's `issues_search` and `issues_import`); each linked issue gets one Puck status comment edited in place; published pull requests carry `Closes owner/repo#n` (or `Refs` when merging would not close the issue), and a merged pull request moves its item to done; CI results (checks, commit statuses, and the redacted names, summaries, and log tails of failed jobs) and review feedback from people with write access reach the orchestrator as notices, read with `ci_read` and `pr_read`, while comments from anyone else never reach an agent; `policies.github.ci: fix` and `reviews: address` also queue follow-ups to the worker; and the Puck server mints environment tokens without the Workflows permission unless `policies.github.allowWorkflowEdits` is true.
- GitHub permission grants, definition updates and CI tracking in the environment daemon stay consistent when a call fails, hangs or repeats: a definition update whose token permissions the server committed but did not confirm puts the previous permissions back (or, when that fails too, syncs them on the next update, across restarts), each policies request gives up after 15 seconds so a hung connection no longer blocks `definition.apply`, the server tells the app about committed permissions even when its audit write fails, publishing the same pull request's same head again no longer resets its CI watch (no repeated notice or `ci: fix` attempt), a new pull request for that commit starts a new watch, a failed job log that could not be read is read again on the next polls before the failure is reported (those retries do not carry into a later failure), and a permissions update still tells the app when the instance view cannot be built.

## 0.0.1 - unreleased

The first public build of Puck: macOS on Apple silicon, macOS 12 or later.

### What the build contains

- A desktop client for coding agents, with Claude Code and Codex as providers.
- One long-lived, Slack-style conversation per agent, stored as a structured event log and replayed on launch.
- Docker environments: persistent containers with one host folder mounted at `/workspace`.
- Provider sign-in in the system browser with a loopback callback.
  Tokens are encrypted through the macOS Keychain, and Puck refuses to store them in plaintext.
- Disconnect removes Puck's own tokens and the credential copies in running environments.
- Streaming turns with markdown, tool cards, sub-agent chats, and answerable question cards.
- A diagnostic log in the app data folder, bounded to three files of 1 MiB.
- A support-bundle export in Settings → Support: the logs plus a sanitized configuration summary.
- An application icon.

### Known limitations

- Codex sub-agents show their lifecycle only (spawned, running, finished), not their transcript.
- The build is ad hoc signed and not notarized until Developer ID credentials exist (open call C-3).
  macOS asks for a one-time approval in System Settings on first launch.
- There are no automatic updates.
  Replace `Puck.app` by hand, as the README describes.
- The distribution channel is not decided (open call C-2).
  The artifact is a local ZIP with a SHA-256 checksum file beside it.
- Environments run agents as root with full tool access inside the container.
  The mounted workspace folder is writable from the container.
- Delete asks for a second click, but rebuild acts on the first click.
